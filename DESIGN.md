# Дизайн приложения Country Search

## 1. Отмена устаревших запросов

### В чем проблема

Если пользователь быстро вводит `sp`, а следом дописывает `spain`, уходит два запроса. По `sp` сервер вернет огромный список стран и, скорее всего, ответит медленнее, чем по конкретному `spain`. Если это не контролировать, ответ на старый запрос придет позже и перезапишет актуальный результат. В итоге в поиске написано `spain`, а на экране висит куча лишних стран по запросу `sp`.

### Как решил

Для каждого нового запроса создается свой `AbortController`, а контроллер поиска (`searchController.ts`) хранит ссылку только на самый свежий из них.

Работает это так: новый ввод -> вызов `abort()` для прошлого запроса и сброс таймера -> пауза 300 мс (debounce) -> новый `AbortController` -> запрос `fetch(signal)`.

Основные моменты реализации:

- Отмена срабатывает сразу при нажатии клавиши, а не после debounce. Иначе за эти 300 мс ожидания старый ответ мог бы успеть прилететь и мелькнуть на экране под новым текстом.
- Использую именно `abort()`, а не обычный флаг «результат устарел». Флаг просто прячет данные, но запрос продолжает висеть, тратить трафик и занимать соединение. `abort()` реально обрывает его на уровне браузера (во вкладке Network он получает статус `canceled`).
- Отмена не считается ошибкой. Функция `classifyError` помечает её как `cancelled`, после чего `runSearch` просто тихо завершается без отрисовки, чтобы не затереть свежие данные.
- Разделил отмену пользователем и таймаут. Сигнал от `AbortSignal.timeout(8000)` и пользовательский сигнал склеиваются через `AbortSignal.any`. Это позволяет сохранить исходную причину (`AbortError` или `TimeoutError`) и показать сообщение об ошибке только при реальном таймауте.
- 404 от сервера — это норма, а не ошибка. API в таком случае отдает текст `Country not found`. Функция `searchCountries` просто возвращает пустой массив `[]`, а UI рисует заглушку «Ничего не найдено». Статус проверяю до парсинга тела, чтобы не упасть при попытке прочитать обычный текст как JSON.

## 2. Задержка debounce: 300 мс

- Без задержки запрос летел бы на каждый символ. Это создает лишнюю нагрузку на API, заставляет список постоянно перерисовываться и плодит кучу запросов, которые тут же приходится отменять.
- Слишком большая задержка (например, секунда) создает ощущение, что приложение тормозит: человек уже закончил печатать, а экран всё ещё пустой.
- 300 мс — это примерно средняя пауза между нажатиями при обычном наборе текста. Пока пользователь печатает слово, запросы не уходят, а как только он остановился — результат подгружается почти мгновенно.

Сам debounce вынес в отдельную утилиту с методом `cancel()`. Это нужно, чтобы контроллер мог сбросить отложенный запуск поиска, если пользователь стер весь текст из поля.

## 3. Сложность (Big O)

- `debounce` - Тут сложность O(1) и по времени, и по памяти. Обычная работа с таймером, никаких циклов и выделения лишней памяти нет.
- `mapCountryResponse` - Сложность O(l + c + b) по времени и памяти, где l, c и b — это количество языков, валют и граничащих стран у одной конкретной страны. Просто проходимся по этим массивам и приводим данные к нужному виду.
- `searchCountries` - Сложность O(n * k) по времени и памяти, где n — количество найденных стран, а k — небольшая константа на обработку полей одной страны (те самые языки и валюты).
- Отрисовка списка - Сложность O(n) по времени и памяти, так как для каждой из n стран нужно создать и добавить в DOM свой элемент списка.

Но вообще, самое узкое место здесь — это сеть, а не алгоритмы в JS. Именно поэтому основной упор сделан на debounce и отмену запросов, чтобы не гонять лишний трафик.

## 4. Принципы чистого кода

- Одна задача на модуль (Single Responsibility) - Файлы `debounce.ts`, `errors.ts` и `mapCountryResponse.ts` отвечают каждый строго за свою маленькую задачу, не превращаясь в свалку логики.
- Разделение логики и интерфейса - `searchController.ts` вообще ничего не знает про DOM и браузер, благодаря чему его удобно покрывать юнит-тестами. А `main.ts` работает только как слой отрисовки, реагируя на смены состояний.
- Сеть в одном месте - Вызов `fetch` спрятан только внутри `searchCountries`. За счет этого в тестах достаточно подменить глобальный `fetch`, и не нужно мокать полприложения.
- Без дублирования (DRY) - Вся логика разбора ошибок собрана в одном месте (`classifyError`), вместо того чтобы размазывать однотипные проверки через `if` по разным функциям.
- Говорящие имена - Функции названы так, чтобы сразу было понятно, что они делают: `cancelCurrentRequest`, `mapCountryResponse`, `createCountryItem`.
- Явные состояния - `SearchState` описан как объединение типов (discriminated union). TypeScript сам следит за тем, чтобы к массиву стран нельзя было обратиться, если статус сейчас не `success`.
- Защита от кривых данных - `mapCountryResponse` не падает, если с бэкенда пришло не всё, что мы ожидали, и аккуратно обрабатывает отсутствующие поля.
- Безопасность - В коде вообще не используется `innerHTML`. Все данные, которые приходят от API, вставляются в разметку строго через `textContent`.

## 5. Как проверялась работа

- Код писался по TDD: сначала делал красный коммит с тестами и пустыми заглушками, и только потом писал саму реализацию до зеленых тестов.
- Для проверки гонки запросов написал отдельный тест с моковым `fetch`, который умеет слушать `signal`. Так проверяется именно реальная отмена старого запроса, а не просто порядок прихода ответов.
- Перед тем как считать задачу готовой, прогнал всё по ручному чек-листу из описания PR.
